# Preexisting non bazel2gn dependency visibility and wrapper scope

- **Learned from:** inner loop friction on a local task (task `src_lib_fostr`)
- **Date:** 2026-10-18
- **Changed:** `checks/bazel_minimality.sh`, `checks/visibility_audit.sh`, `tools/find_rdeps.sh`

## Root cause

When a migrated target depends on a pre-existing BUILD.bazel package outside the
target directory whose BUILD.gn is not managed by bazel2gn (no BAZEL2GN
SENTINEL), visibility_audit and find_rdeps counted all BUILD.gn callers of the
hand-written GN target toward the Bazel target's rdeps (misclassifying it as
globally used and demanding tree-wide visibility), while bazel_minimality
flagged pre-existing unwrapped cc_library rules in that dependency's BUILD.bazel
even though the target definition predated the change.

## Why not a one-off fix

Exempting only a single dependency package path would fail whenever any future
migration adds a caller visibility entry to another pre-existing hand-maintained
BUILD.bazel package whose BUILD.gn is not generated by bazel2gn or still uses
unwrapped rules from before the migration.
