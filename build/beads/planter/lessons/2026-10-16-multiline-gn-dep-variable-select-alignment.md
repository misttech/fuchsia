# Multiline gn dep variable select alignment

- **Learned from:** inner loop friction on CL I23bcc8a7f5bc6f91ed74246eb860b9ca45e8e24b, patchset 1 (task `netstack3-trace`)
- **Date:** 2026-10-16
- **Changed:** `checks/migration_sanity.sh`

## Root cause

record_multiline_gn_dep_alignment_info in checks/migration_sanity.sh only
matched `=` list literals when collecting GN helper variables below the BAZEL2GN
SENTINEL, ignoring conditional `+=` appends generated by bazel2gn from top-level
Starlark select() dependency variables. As a result, targets whose `deps =` line
was wrapped by `gn format` (such as inside `if (is_host)`) failed the full
GN-to-Bazel dependency equality check whenever a shared dependency variable used
`select()`, leaving review_diff's false-positive single-line `dep_alignment`
warning uncovered.

## Why not a one-off fix

Any dual-build package that defines a top-level Starlark dependency variable
using `select()` (translated by `bazel2gn` to `_VAR = []` followed by `if (...)
{ _VAR += [...] }`) and references it in a `deps =` concatenation wrapped onto
the next line by `gn format` will hit the same false-positive `dep_alignment`
warning unless `migration_sanity.sh` evaluates both `=` and `+=` GN variable
assignments.
