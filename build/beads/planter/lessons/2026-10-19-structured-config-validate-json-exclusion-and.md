# Structured config validate json exclusion and manifest rule parity

- **Learned from:** inner loop friction on a local task (task `pkg-system-update-checker`)
- **Date:** 2026-10-19
- **Changed:** `checks/build_verification.sh`, `checks/migration_sanity.sh`, `checks/visibility_audit.sh`, `tools/find_rdeps.sh`, `tools/run_checks.sh`

## Root cause

First, build_verification.sh only excluded <name>_validate_ir_json targets
generated directly by fidl_library and validate_json macros when running fx
bazel build :all, missing <name>_fidl_internal_validate_ir_json generated by the
internal fidl_library inside fuchsia_structured_config_rust_lib, which caused
assert_no_deps_aspect to crash on its scalar data attribute. Second,
migration_sanity.sh and run_checks.sh only matched diffengine (Target
Attributes) clauses in is_benign_attribute_alignment, failing to suppress benign
(Rule & Directives) warnings for fuchsia_* to fx_* component/manifest rule
mappings. Third, visibility_audit.sh and find_rdeps.sh classified pre-sentinel
GN group() targets as gn_nonconvertible_targets even when a same-named alias()
target existed in BUILD.bazel.

## Why not a one-off fix

Any Fuchsia component package that uses fuchsia_structured_config_rust_lib with
fx_component_manifest or depends on a dual-build library exposing a Bazel
alias() alongside a pre-sentinel GN group() will hit the same
assert_no_deps_aspect :all crash, review_diff rule-mapping warning, and rdep
exclusion unless the check and rdep machinery handle these general rule
patterns.
