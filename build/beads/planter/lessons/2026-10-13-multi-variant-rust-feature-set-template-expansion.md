# Multi-variant Rust feature-set template expansion parity and unrelated pre-existing GN Ninja build failure isolation

- **Learned from:** inner loop friction on a local task (task `netstack3-sync2`)
- **Date:** 2026-10-13
- **Changed:** `checks/build_verification.sh`, `checks/gn_target_type_parity.sh`, `checks/manifest.json`

## Root cause

First, gn_target_type_parity treated rustc_library_with_features as an opaque
template and flagged its dual-build migration to explicit rustc_library targets
(generated by bazel2gn alongside rustc_check_cfg_build_flags) as an invalid GN
target type change, even when the base target and all of its feature_sets
target_name variants were emitted as rustc_library targets. Second,
build_verification's unrelated_bazel_failure only recognized out-of-sync Bazel
action failures in other git repositories and treated pre-existing upstream
native GN/Ninja compile failures in unrelated packages with no dependency path
to any changed directory as blocking gn_build errors, skipping
gn_build_dependents.

## Why not a one-off fix

Hardcoding a single crate name or ignoring a specific failing target path would
fail on every subsequent migration of crates that use
rustc_library_with_features or encounter unrelated upstream Ninja compile errors
at the base revision; recognizing rustc_library_with_features expansion when all
feature_sets variants are emitted as rustc_library and verifying via Ninja step
headers and --transdeps that native GN build failures have no dependency on any
changed package fixes both classes of friction across the entire repository.
